# laser-mtproxy

[English](README.md) | Русский

MTProto-прокси для приложений Telegram и шлюз Bot API для ботов на `laser_tele`. Сервер работает на отдельной
машине в локальной сети, управляется через веб-интерфейс. Это перенос
[tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy) на Go: те же маршруты к Telegram, вместо трея веб-интерфейс.

```
Telegram Desktop / телефон ──MTProto (dd/ee)──► :1443 ─┬─► wss://kwsN.web.telegram.org (пул, DC → IP)
                                                       ├─► CF Worker ─► IP датацентра
                                                       ├─► CF-домены: WebSocket, медиа по HTTP/2
                                                       └─► TCP к IP датацентра
бот на laser_tele ──HTTP CONNECT / SOCKS5──► :1080 ──► api.telegram.org:443 (DNS, запасные IP, CF Worker)
администратор ──браузер──► :8080 (веб-интерфейс)
```

Боты работают с Bot API по HTTPS, поэтому MTProto-прокси им не подходит. Для них на отдельном
порту работает HTTP CONNECT и SOCKS5 прокси, который открывает туннели только к разрешённым адресам
(`api.telegram.org:443`). TLS остаётся сквозным: шлюз видит только зашифрованный поток.

## Запуск

Нужен Go 1.24 или новее. Единственная внешняя зависимость — `github.com/boombuler/barcode` для QR-кодов.

```
cd mtproxy
go build -o laser-mtproxy .
cp dist/laser-mtproxy.json .
./laser-mtproxy -config laser-mtproxy.json
```

При первом запуске сервер создаёт секреты пользователей, записывает их в конфиг и печатает ссылку `tg://proxy?...`
первого пользователя.
Веб-интерфейс: `http://<IP машины>:8080`. Если конфига нет, он создаётся со значениями по умолчанию.

Сборка под Linux, Windows и macOS: `./build.sh` (результат в `build/`).

Флаги: `-config путь`, `-v` (подробный лог), `-check` (проверить конфиг, не меняя его), `-version`,
`--install`, `--uninstall`, `--purge`.

## Установка сервисом systemd

```
./laser-mtproxy --install                          # конфиг по умолчанию
./laser-mtproxy --install -config my-config.json   # начальный конфиг
```

| Кто запускает | Сервис | Каталог (бинарник, конфиг, логи, статистика) | Лог |
|---|---|---|---|
| обычный пользователь | пользовательский, `~/.config/systemd/user/laser-mtproxy.service` | `~/.local/share/laser-mtproxy` | `journalctl --user -u laser-mtproxy` |
| root | системный, `/etc/systemd/system/laser-mtproxy.service`, работает от системного пользователя `laser-mtproxy` | `/opt/laser-mtproxy` | `journalctl -u laser-mtproxy` |

Повторный `--install` обновляет бинарник и перезапускает сервис; конфиг, если он уже есть, не трогается
(`-config` нужен только при первой установке). Чтобы пользовательский сервис работал после выхода из системы,
установщик включает linger (`loginctl enable-linger`), а если не хватает прав, печатает команду для root. Системный сервис может
слушать порты ниже 1024 (например, 443 для Fake TLS).

`--uninstall` останавливает и удаляет сервис, конфиг с секретами, логи и статистика остаются;
`--uninstall --purge` удаляет и их (а у системного сервиса ещё и пользователя `laser-mtproxy`).

## Доступ и пароли

Конфиг поставки доверяет этой машине и её локальной сети:

```json
"access": {
  "trusted_networks": ["loopback", "lan"],
  "username": "admin"
}
```

`lan` означает частные подсети сетевых интерфейсов машины (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7,
link-local), сервер пересчитывает их раз в минуту. Публичная подсеть сервера в датацентре в `lan` не входит.
Ещё в списке могут быть `private` (все частные адреса), `any` (все адреса), CIDR (`10.0.0.0/8`) и отдельные IP.

| Вход | Доверенный адрес | Остальные адреса |
|---|---|---|
| Веб-интерфейс | без пароля | закрыт (`web.admin_trusted_only`, по умолчанию); если выключить — логин и пароль |
| Личные страницы `/p/<токен>` | открываются | открываются (ключ — токен в адресе) |
| Шлюз Bot API | без пароля | `http://admin:пароль@host:1080` или SOCKS5 с логином и паролем |
| MTProto | все включённые пользователи | только пользователи с `"allow_external": true` |

У MTProto нет пароля: клиент шифрует подключение секретом пользователя. Пока не задан пароль, веб-интерфейс и шлюз
недоступны с недоверенных адресов. Пароль задаётся в веб-интерфейсе или в конфиге полем `"password": "..."`
внутри `access`: при запуске сервер заменяет его хешем `password_hash`.

Если пользователь без `allow_external` подключается с чужого адреса, подключение отклоняется, в лог пишется
предупреждение, в отчёте растёт счётчик «не из сети».

## Пользователи

У каждого пользователя свой секрет и свой лимит одновременных подключений:

```json
"users": [
  {"name": "lan",   "secret": "", "max_connections": 100, "allow_external": false, "comment": "общий секрет для локальной сети"},
  {"name": "ivan",  "secret": "", "max_connections": 12,  "allow_external": true},
  {"name": "guest", "secret": "", "max_connections": 0,   "allow_external": false}
]
```

- `max_connections`: `0` — пользователь выключен, `N` — до N одновременных подключений. Сверх лимита новое
  подключение закрывается, в отчёте растёт счётчик «лимит».
- Одно приложение Telegram держит несколько подключений: основное и отдельные для загрузки медиа. Ставьте лимит
  с запасом, например 10–20 на устройство, и смотрите пик в отчёте.
- Пустой `secret` сервер заполняет случайным при запуске или сохранении.
- `allow_external`: пускать пользователя не только из доверенных сетей.

Пользователей удобнее вести на вкладке «Пользователи»: добавить, изменить лимит, выключить, создать новый секрет,
удалить. Изменения действуют сразу, прокси не перезапускается. Если пользователя выключить, удалить или сменить ему
секрет, его текущие подключения обрываются; уменьшение лимита открытые подключения не трогает.

Секрет и есть пользователь: кто получил ссылку, подключается от его имени. Отличить пересылку ссылки нельзя,
но её выдаёт отчёт (несколько адресов сразу, упор в лимит). Тогда выдайте новый секрет.

Конфиг версии 1.0 с `secret` и `external_secret` переносится автоматически: они становятся пользователями
`lan` и `external`, ссылки продолжают работать.

### Личная страница с QR-кодом

Кнопка «QR и ссылка» открывает страницу `http://<сервер>:8080/p/<токен>`: QR-код, кнопка «Открыть в Telegram»,
ссылка для копирования, PNG с кодом и параметры для ручной настройки. Кнопка «Адрес страницы» копирует её адрес,
его можно отправить человеку. Пароль странице не нужен, а токен получается из секрета, угадать его нельзя.
После «Новый секрет» старая страница перестаёт работать.

В ссылках пользователей с `allow_external` стоит `public_host`, если он задан, иначе адрес, по которому открыта
страница. Для внешних пользователей задайте `public_host` (внешний IP или имя).

### Отчёт

Вкладка «Отчёт»: по каждому пользователю подключения сейчас и лимит, пик и его время, число подключений,
отказы (лимит, выключен, не из сети), трафик, последнее подключение с адресом, адреса текущих подключений.
Счётчики сохраняются раз в минуту и при остановке в `laser-mtproxy-stats.json` рядом с конфигом.
Отчёт можно скачать в CSV (открывается в Excel) и обнулить.

### Прокси снаружи, админка только изнутри

1. `host: "0.0.0.0"`: MTProto слушает все адреса, включая публичный.
2. `public_host`: публичный адрес или имя сервера, он попадёт в ссылки внешних пользователей.
3. Пользователям, которым нужен доступ снаружи, ставится `allow_external: true`; их секрет и есть пароль.
   Остальные снаружи отклоняются.
4. `web.host`: локальный адрес, чтобы админка не слушала публичный. С `web.admin_trusted_only: true` админка
   не отвечает недоверенным адресам, даже если веб-порт откроют наружу; там работают только личные страницы.
5. Шлюз Bot API снаружи открывать не обязательно: в `gateway.host` укажите локальный адрес.

С доверенного адреса веб-интерфейс открывается только по IP, `localhost` или имени этой машины, другие имена
добавьте в `web.allowed_hosts`. Так закрыт DNS rebinding: чужой сайт не сможет управлять прокси через браузер
человека из локальной сети.

## Подключение Telegram

Отправьте человеку адрес его личной страницы или покажите QR-код. С телефона проще всего открыть страницу и нажать
«Открыть в Telegram». Вручную: Настройки → Продвинутые → Тип подключения → Прокси → MTProto, сервер, порт и секрет
со страницы.

Если не грузятся фото и видео, оставьте в «DC → IP» только `4:149.154.167.220` или очистите поле.

## Подключение бота

```go
laser_tele.DoLaserTeleInit(laser_tele.LaserTeleConfigT{
	Proxy: "http://192.168.1.10:1080", // или socks5://192.168.1.10:1080
})
```

или переменная окружения `TG_PROXY=http://192.168.1.10:1080`. С недоверенного адреса:
`http://admin:пароль@192.168.1.10:1080`.

Шлюз подключается к `api.telegram.org` по адресу из DNS, через 1,5 секунды параллельно пробует запасные IP
из `gateway.fallback_ips` и запоминает сработавший адрес. Фронтенды Telegram (`149.154.167.220` и другие)
отдают и Bot API с действительным сертификатом `api.telegram.org`, поэтому шлюз работает и там, где адрес
`api.telegram.org` заблокирован. Последний запасной путь — CF Worker (`gateway.via_cfproxy_worker`).

## Проверка

`mtprobe` подключается к прокси как клиент Telegram, отправляет `req_pq_multi` в датацентры и ждёт `resPQ`
от настоящего Telegram:

```
go run ./cmd/mtprobe -addr 192.168.1.10:1443 -secret dd<секрет> -dc 1,2,3,4,5,-2,-4
DC1        OK    resPQ in 532 ms
DC2        OK    resPQ in 45 ms
...
```

Отрицательный номер означает медиа-DC. Для ee-секрета передайте его целиком, `mtprobe` пройдёт Fake TLS.
Шлюз проверяется так: `curl -x http://192.168.1.10:1080 https://api.telegram.org/bot123:x/getMe` должен вернуть
`{"ok":false,"error_code":401,...}` — это ответ настоящего Bot API.

Вкладка «Проверка» веб-интерфейса проверяет прямой маршрут DC → IP, CF-домены и CF Worker.

## Конфигурация

Названия полей MTProto-части те же, что в tg-ws-proxy.

| Поле | По умолчанию | Назначение |
|---|---|---|
| `host`, `port` | `0.0.0.0`, `1443` | адрес MTProto-прокси |
| `public_host` | пусто | адрес в ссылках внешних пользователей; пусто — адрес, по которому открыт веб-интерфейс |
| `users` | `lan` на 100 подключений | пользователи: `name`, `secret`, `max_connections`, `allow_external`, `comment` |
| `dc_ip` | `2:149.154.167.220`, `4:149.154.167.220` | прямой WebSocket-маршрут к DC |
| `pool_size`, `buf_kb` | `4`, `256` | готовые WS-соединения на DC; буфер сокета |
| `cfproxy`, `h2` | `true`, `true` | запасной путь через CF-домены; медиа по HTTP/2 |
| `cfproxy_user_domain_enabled`, `cfproxy_user_domain` | выкл. | свои CF-домены вместо встроенных |
| `cfproxy_domains_url` | список tg-ws-proxy на GitHub | обновление списка CF-доменов раз в час, пусто — только встроенный |
| `cfproxy_worker_enabled`, `cfproxy_worker_domain` | выкл. | домены Cloudflare Worker |
| `no_secure` | `false` | порт 80 без TLS для CF-прокси и Worker |
| `force_test_dc` | `false` | весь трафик на тестовые DC |
| `fake_tls_domain` | пусто | Fake TLS (ee-секрет) и маскировка под сайт |
| `proxy_protocol` | `false` | заголовок PROXY v1 от nginx/haproxy (принимается только от доверенного адреса) |
| `verbose`, `log_file`, `log_max_mb` | `false`, `laser-mtproxy.log`, `5` | лог; путь относительно конфига |
| `access.*` | см. выше | доверенные сети, логин, пароль |
| `gateway.enabled`, `host`, `port` | `true`, `0.0.0.0`, `1080` | шлюз Bot API |
| `gateway.allowed_hosts` | `api.telegram.org:443` | куда шлюз открывает туннели: `host:port`, `*.domain:port`, порт `*` |
| `gateway.fallback_ips` | `api.telegram.org: 149.154.167.220` | запасные адреса хостов |
| `gateway.via_cfproxy_worker` | `true` | последний запасной путь шлюза через CF Worker |
| `web.host`, `web.port` | `0.0.0.0`, `8080` | веб-интерфейс (применяется после перезапуска процесса) |
| `web.tls_cert`, `web.tls_key` | пусто | HTTPS для веб-интерфейса |
| `web.language` | `ru` | язык по умолчанию |
| `web.allowed_hosts` | пусто | дополнительные имена хоста веб-интерфейса |
| `web.admin_trusted_only` | `true` | администрирование только из доверенных сетей, вход по паролю снаружи запрещён |

Как настроить Cloudflare Worker и свой CF-домен, описано в документации tg-ws-proxy (`docs/RU/CfWorker.md`,
`docs/RU/CfProxy.md`); код воркера тот же.

## Отличия от tg-ws-proxy

- Вместо трея и окна настроек — веб-интерфейс: ссылки, перезапуск, настройки, тесты CF, статистика, логи.
- Доверенные сети и пароль.
- Пользователи со своими секретами и лимитом подключений, личные страницы с QR-кодом, отчёт.
- Шлюз Bot API для ботов.
- Нет проверки обновлений приложения и автозапуска Windows; для Linux есть unit systemd.
